# poirot 测试完善计划

- 日期：2026-08-25
- 依据：当日项目测试分析（现状基线见 §1，数据出处见 §9）
- 范围：本期**不含 CI 流水线**（暂缓原因见 §8）
- 约束：计划期内**不修改业务代码**（`poirot/backend/agents/`、`poirot/backend/app/`），只新增/调整测试与工程配置；如测试暴露出业务缺陷，单独记录、另行决策

核心矛盾：**数量庞大（2721）但金字塔倒置**——单元占 98.7%，集成 2.1%，真实链路趋近 0；且无度量、无门禁、非全绿。

## 2. 目标

生产级测试体系，定义为五个可验收特征：

1. **全绿**：`pytest` 全量通过，无已知失败
2. **可度量**：覆盖率有数字，并设门禁（起步 80%）
3. **层级平衡**：集成层与真实链路测试占比显著提升
4. **有专项**：可靠性、性能、安全、评估四类生产级专项各有覆盖
5. **自工程化**：测试自身的隔离性、异步覆盖、mock 质量可控

## 4. P0 测试可运行性基建

> 本阶段全部为"修测试 + 加工具配置"，不触碰业务代码。

### P0-1 14 个失败测试清零

| # | 失败组 | 根因 | 修法 | 涉及业务代码 |
|---|---|---|---|---|
| 1 | test_config_loader（max_loop_steps） | 断言过期：代码 EXPERT_PROFILE 已改 100，测试仍断言 8；profiles/*.yaml 为废弃遗留 | 修正断言（或参数化跟随配置源） | 否 |
| 2 | test_merge_sandbox（state 字段数） | 代码新增 recalled_memories/memory_updates 字段，断言未跟随 | 更新字段集合断言 | 否 |
| 3 | test_default_strategy（"对话历史"） | 模板已改英文，测试仍断言中文 | 同步为模板当前语言 | 否 |
| 4 | test_claude_credential（6 用例） | Claude Code 注入 ANTHROPIC_AUTH_TOKEN 污染；部分用例未清理该变量 | 统一用 monkeypatch 清理/隔离（参照已有 3 个用例的写法） | 否 |
| 5 | test_pi_installer（4）+ test_bash_output_truncation（1） | 顺序依赖：依赖前面测试残留状态 | 每个用例自建依赖状态（独立 setup/teardown） | 否 |

- **验收**：全量 `pytest` 零失败（2704 通过基线之上），且随机顺序下复跑通过
- **预估**：0.5~1 天（多数是断言值与清理逻辑的小修）
- **产出**：失败明细记录一份（修前截图/输出存档，作为回归对照）

### P0-2 覆盖率量化 + 门禁

- **内容**：dev 依赖加 `pytest-cov`；pyproject 加 `[tool.coverage]` 配置；首次全量跑出**基线数字**（当前未知，预期模块间差异大：sandbox/multiagent 高，prompts 趋近 0）
- **门禁**：`--cov-fail-under=80`（起步线），重点模块（sandbox/multiagent/memory）单独报告，目标 85%+
- **产出物**：`coverage/` 报告目录（html 供人工查看）、基线数字写入本计划附录
- **涉及业务代码**：否
- **验收**：`pytest --cov=poirot --cov-fail-under=80` 一次通过；prompts 等低覆盖模块出现在报告中成为可见短板
- **预估**：0.5 天

### P0-3 pytest 规范化

| 子项 | 内容 | 解决什么 |
|---|---|---|
| conftest.py | 新增 `tests/conftest.py`：workspace 临时目录 fixture（收拢各文件自写的 `_workspace_temp_dir`）、fake model fixture（收拢 FakeChatModelWithTools 构造） | 重复代码；临时目录规则不一（顺序污染温床） |
| pytest 配置 | pyproject 加 `[tool.pytest.ini_options]`：`asyncio_mode`、`anyio_backend`、`testpaths`、markers 注册 | 异步测试无运行规则；35 处 anyio 标记形同虚设 |
| pytest-randomly | dev 依赖加 `pytest-randomly`，打乱顺序暴露隐藏依赖 | test_pi_installer 类问题从"偶尔发现"变"必然暴露" |

- **涉及业务代码**：否（仅新增测试文件与配置）
- **验收**：随机顺序下全量绿；conftest fixture 被 ≥10 个测试文件复用；异步测试可明确运行
- **预估**：1 天（含把现有临时目录逻辑迁移到 fixture 的重构）

## 5. P1 测试层级补强

> 目的：把 98.7% 的单测金字塔压向"单测为主、集成成体系、真实链路可回放"。

### P1-1 集成测试补强（56 → 100+）

- **内容**：
  - 持久化集成：日志/记忆/评估 DB 的真实读写链路（当前多为内存或假实现）
  - 并发集成：跨进程锁、文件操作锁的真实并发场景
  - MCP 链路：用本地 fake MCP server（stdio 协议）走完整加载→调用→审计链路
  - 上下文治理：真实多轮会话下 strategy 的组装与 token 预算行为
- **涉及业务代码**：否（如暴露缺陷则记录，另行决策）
- **验收**：集成测试占比从 2.1% 提升至 ≥5%；每条链路有"真实组件组合"用例
- **预估**：3 天

### P1-2 真实 LLM 回放测试（VCR 模式）

- **内容**：录制真实 DeepSeek 调用的请求/响应（VCR 类方案），CI 与本地重放不花钱、不联网；把现有 `test_p4_summarize_real`（需 key 才跑）纳入回放体系，改为"有 key 时录制、无 key 时回放"
- **涉及业务代码**：否（新增录制脚本与测试）
- **验收**：一套覆盖"研究→报告"主链路的回放测试，无 key 环境可稳定运行
- **预估**：2 天

### P1-3 盲区补测

| 模块 | 现状 | 目标 |
|---|---|---|
| agents/prompts（manager.py + system 模板） | **0 个测试** | 模板渲染、变量注入、版本兼容 ≥20 用例 |
| journal（run_journal） | 1 文件 | 事件写入/读取/损坏容错 ≥15 用例 |
| artifacts（local_store） | 1 文件 | 读写/覆盖/清理/非法路径 ≥10 用例 |
| capabilities（registry） | 2 用例 | 注册/查询/冲突 ≥10 用例 |
| app/tui | 7 用例 | 关键交互（输入循环、命令分发）补到 ≥20 |

- **涉及业务代码**：否（新增测试；如发现行为缺陷则记录）
- **验收**：上表目标用例数达成；prompts 模块覆盖率从 ~0% 升至 ≥60%
- **预估**：3 天

## 6. P2 生产级专项

### P2-1 性能/压力基准（bench）

- **内容**：agent 循环耗时基准、上下文 token 预算越界行为、超长输出截断、递归上限触发、内存不增长（长会话冒烟）
- **产出物**：`bench/` 目录 + 基准数据快照（对比基线）
- **涉及业务代码**：否
- **验收**：5 项基准各有用例；耗时变化 >20% 有告警机制
- **预估**：2 天

### P2-2 可靠性/故障注入

- **内容**：LLM 超时、HTTP 500、流中断、部分失败（单个 subagent 挂掉整体行为）、重试与退避策略
- **涉及业务代码**：**可能**——如发现重试/降级逻辑缺失，记录缺陷但本计划期内不修，单独决策
- **验收**：每个故障点 ≥1 用例，断言"可恢复或明确报错"而非悬挂
- **预估**：3 天

### P2-3 评估基准集（eval dataset）

- **内容**：利用产品自带 `multiagent/eval` 框架，新建 `resource/eval_tasks/`：20~50 个典型研究任务（如"对比 A 与 B""调研 X 现状"），每个任务含输入、期望维度、评分口径；配套回归运行脚本输出分数快照
- **涉及业务代码**：否（新增数据资产与脚本）
- **验收**：≥20 个 golden 任务入库；回归脚本可一键出分；首次分数记录为基线
- **预估**：3~5 天（任务编写是主要成本）

### P2-4 安全对抗测试

- **内容**：在 sandbox 既有 614 个安全用例基础上补：提示注入、路径穿越 fuzz、凭据泄露回归（每次安全修复必须带用例）
- **涉及业务代码**：否（新增对抗性用例）
- **验收**：注入/穿越/泄露三类各 ≥5 个对抗用例；与既有 selfcheck 批次合并运行
- **预估**：2 天

### P2-5 兼容性矩阵

- **内容**：Python 3.12/3.13 双版本验证；Linux 路径/换行/权限差异验证（Docker 环境，当前本机未装 Docker，标注为环境前置）
- **涉及业务代码**：否
- **验收**：双版本全量绿；Linux 冒烟通过
- **依赖**：Docker 环境或 CI（暂缓，见 §8）——**本项在环境就绪前挂起**
- **预估**：1~2 天（环境就绪后）

### P2-6 打包/分发冒烟

- **内容**：干净 venv 中 `pip install .` → entry point 可用 → `poirot run --help` 冒烟；Docker build 成功后 `docker run` 冒烟（同样依赖 Docker 环境）
- **涉及业务代码**：否
- **验收**：干净环境安装后 CLI 可用；Docker 镜像可构建可启动
- **预估**：1 天（Docker 部分待环境）

### P2-7 可观测性断言

- **内容**：`events.jsonl` 事件 schema 断言、journal 完整性、运行记录与报告产物一致性
- **涉及业务代码**：否
- **验收**：事件流每类事件有 schema 校验用例；损坏/截断文件的容错用例
- **预估**：1 天

- **涉及业务代码**：否
- **验收**：P3-1 达标；P3-2 抽查报告产出；P3-3 后随机顺序连续 3 次全绿
- **预估**：2~3 天

## 8. 暂缓项：CI 流水线

- **决定**：本期不做。原因：CI 需要提交 `.github/workflows/` 并依赖远程仓库（GitHub 直连受限），且用户本期不修改项目代码、以本地学习验证为主
- **保留理由**：CI 仍是生产级最终门禁（标准环境 + 强制关卡 + 团队可见），后续时机：发布首个版本、多人协作、或网络条件改善
- **衔接**：本计划产出的全部工具（覆盖率门禁、randomly、回放测试、评估脚本）在本地验证通过后，可原样搬入 CI 流水线，无需重写
